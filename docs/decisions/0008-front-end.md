# ADR 0008: The front end of iteration 4

- **Status:** accepted. Built in the front-end session and merged in PR #19; approved by Luis on
  2026-10-12 in the documentation pull request.
- **Date:** 2026-10-11
- **Details:** `frontend/README.md`; the gaps it found are in `frontend/FINDINGS.md` (F-01 to F-11)
  and in the shared improvements list.

## Context

Iteration 4 puts a product on the iteration 3 API: intake, a review queue and workbench,
compliance, a receipt history, insights and an evaluation area, with the Ledgerline design
(`docs/design/`). The front end decides nothing: every verdict comes from the API's deterministic
engine.

## Decisions

1. **React, Vite and TypeScript**, with tokens generated from `docs/design/tokens.json` by a
   script (light, dark and a manual theme switch). The generated CSS is git-ignored.
2. **Same-origin `/api` in development.** The browser calls `/api`, which the Vite dev and preview
   servers proxy to the API (`EPV_API`, default `http://localhost:8000`). The API also answers
   CORS for a listed set of origins (ADR 0007 amendment 14), so a deployment may use either that
   or serve the built front end from the API process.
3. **Insights are computed in the browser** from the receipts, their details and their events,
   each figure with its N, until an aggregate endpoint exists (F-02). One figure ("findings on
   receipts where someone disagreed") uses the receipt's current result and is labelled as an
   approximation.
4. **The Evaluation screen reads `public/evaluation.json`**, generated by `npm run evaluation`
   from `outputs/eval/metrics.json` and `experiments.json` (aggregates only) and from
   `frontend/data/classifier-comparison.json`. A unit test fails if the committed file is stale
   or carries a receipt ID or an answer key.
5. **Where the design and the API disagree, the front end follows the API** (reason codes,
   keyboard actions, event names, who may act in Compliance) and records the difference as a
   finding for Luis (F-07, F-11).
6. **The jev-1.13 run is evidence, not a decision.** It ran once on the frozen dev set (N = 130,
   USD 0.0055, traced): 130 of 130 categories, no subtype or recipient. It is not a registered
   experiment and changes no configuration.
7. **Tests:** Vitest for the helpers and for the API contract against `docs/api/openapi.json`;
   Playwright end to end against a backend the test starts on a throwaway database.

## Consequences

- The list view makes one request per visible row (F-01); fine for a demo and a few hundred
  receipts, not for production volume. The summary and aggregate endpoints are in the improvements
  list.
- The category list is a copy of the taxonomy with no drift check (F-05).
- Nothing outside `frontend/` changed in this iteration except the documents of this one.

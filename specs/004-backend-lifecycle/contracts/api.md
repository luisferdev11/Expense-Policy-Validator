# HTTP API contract

Base URL `http://localhost:8000`. JSON in and out. The machine-readable document is FastAPI's
`/openapi.json` (committed as `docs/api/openapi.json`); the Postman collection in `docs/api/`
exercises this file. Every response that carries a receipt carries the **stripped** receipt
only. Money is a string in JSON (`"12.50"`), so no precision is lost; on input, numbers keep the
precision they were written with.

## Error shape

```json
{"error": {"code": "stale_evaluation", "message": "...", "details": {}}}
```

Codes: `invalid_receipt` (422), `invalid_idempotency_key` (422), `idempotency_key_reuse` (422),
`invalid_request` (422, a body or query that fails validation), `invalid_batch` (422),
`invalid_action` (422), `reason_required` (422), `unknown_category` (422), `not_found` (404),
`method_not_allowed` (405), `action_not_allowed` (409), `stale_evaluation` (409).

The machine-readable contract is `docs/api/openapi.json`, generated by `uv run epv openapi`; a test
fails if it is stale.

## Receipts

### `POST /receipts`

Headers: `Idempotency-Key` (optional, at most 255 characters). Body: one receipt (the input
contract of `ReceiptInput`; answer keys are tolerated and discarded).

| Case | Status | Body |
|---|---|---|
| New receipt | 202 | `{"receipt_id", "revision": 1, "outcome": "accepted", "state": "submitted", "superseded": false}` |
| Same key or same content again | 200 | the same, with `"outcome": "existing"`, the receipt's current revision and state; `"superseded": true` when the key belongs to a revision that a newer one replaced |
| Same `receipt_id`, different content, no reused key | 202 | `"outcome": "revision"`, `"revision": n+1`. Going back to earlier content without a key is also a new revision |
| Client key reused with a different body | 422 | `idempotency_key_reuse` |
| Invalid body | 422 | `invalid_receipt`, with the offending fields |

### `GET /receipts`

Query: `state`, `disposition`, `batch_id`, `limit` (default 100), `offset`. Returns
`{"items": [ReceiptSummary], "total": n}`.

### `GET /receipts/{receipt_id}`

```json
{
  "receipt_id": "...", "revision": 2, "state": "in_review", "disposition": "flag",
  "evaluation_version": 3, "notice": null, "qa_sample": false,
  "failed": null,
  "receipt": { "...stripped ReceiptInput..." },
  "result": { "...ReceiptResult as in outputs/results.jsonl..." },
  "allowed_actions": ["approve", "reject", "correct-category", "request-info", "escalate"]
}
```

### `GET /receipts/{receipt_id}/events`

`{"items": [{"seq", "revision", "type", "actor", "at", "payload"}]}` in `seq` order.

### `GET /receipts/{receipt_id}/revisions/{n}`

The revision's stripped content, its status and its evaluation versions.

### `POST /receipts/{receipt_id}/retry`

Retries a receipt in `failed` from the failed stage. `202`; `409 action_not_allowed` otherwise.

## Reviewer actions

`POST /receipts/{receipt_id}/actions/{action}`, `action` one of `approve`, `reject`,
`correct-category`, `request-info`, `escalate`. Common body fields: `actor` (required),
`evaluation_version` (required), `note` (optional).

| Action | Extra fields | Result state |
|---|---|---|
| `approve` | `reason_code` (required when overriding a `flag`) | `approved` |
| `reject` | `reason_code` (required when overriding a `pass`) | `rejected` |
| `correct-category` | `line_id`, `category` | `in_review` or `compliance` (new evaluation version) |
| `request-info` | `question` | `needs_info` |
| `escalate` | `reason` | `compliance` |

Response `200`: the updated receipt (as `GET`), plus `"agreement": 0 or 1`. A stale
`evaluation_version` gives `409 stale_evaluation` with
`details.current_evaluation_version`; a state that does not allow the action gives
`409 action_not_allowed` with `details.state` and `details.allowed`. An unknown action name is
`404`; unknown body fields are refused (`422 invalid_request`).

Reason codes (a closed list): `policy_exception_granted`, `engine_false_positive`,
`engine_missed_issue`, `documentation_provided`, `other` (which needs a `note`). A reason code is
required exactly when the decision overrides the engine's proposal: approving a `flag`, or
rejecting a `pass`. `reject` is allowed from `in_review`, `compliance`, `auto_approved` and
`needs_info`; `approve`, `correct-category` and `request-info` from `in_review` and `compliance`;
`escalate` from `in_review` only.

`correct-category` re-runs the engine inside the same transaction: the response already carries
the new evaluation version. Receipts that share the employee-day or the trip are queued for
re-evaluation by the worker.

## Batches

### `POST /batches`

Body: JSONL (`Content-Type: application/x-ndjson`) or a JSON array (`application/json`), at most
1000 rows (`422 invalid_batch` for an empty or larger batch). Each valid row is submitted on its
own with the rules of `POST /receipts`, so resubmitting a batch starts no new work: every receipt
that exists is reported `existing`. A batch has no key of its own; each resubmission is a new
batch record. Status `202` when every row was accepted, existing or a revision, `207` when some
rows were `invalid` or `duplicate_in_batch`.

Row outcomes: `accepted`, `existing`, `revision`, `invalid` (with `error`), `duplicate_in_batch`.

```json
{"batch_id": "bat_ab12cd34", "total": 3, "counts": {"invalid": 1, "submitted": 2},
 "items": [{"row": 1, "receipt_id": "...", "outcome": "accepted", "error": null,
            "state": "submitted"},
           {"row": 2, "receipt_id": null, "outcome": "invalid",
            "error": "not valid JSON: ...", "state": null}]}
```

### `GET /batches/{batch_id}`

The same shape. `counts` is by the current state of each accepted receipt; rows that stored
nothing are counted under their outcome (`invalid`, `duplicate_in_batch`), so no receipt is
counted twice. An item in `failed` is retried alone with `POST /receipts/{id}/retry`.
`GET /receipts?batch_id=...` lists the batch's receipts.

## Operations

`GET /health` returns `{"status": "ok", "schema_version": 1}`.
